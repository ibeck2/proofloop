## 2. 調査で判明した事実（設計判断の根拠）

### 2.1 `/admin` のセキュリティ実装 — ユーザーの前提と実装が食い違っていた

ユーザーの当初案は「`/admin` にツールを格納し、admin用Gmailに加えて**パスワードを追加**することで脆弱性を排除する」だった。実装を確認した結果、前提が事実と異なる。

- `app/admin/page.tsx:74-76` — **クライアントサイドの `useEffect`** で `profiles.role === 'admin'` を判定し `router.replace("/")` しているだけ。同じパターンが `reviews` `requests` `jobs` にもある。
- **`middleware.ts` は存在しない**（確認済み）。`app/admin/` に `layout.tsx` も無い。
- ⇒ **ページのHTML/JSは誰にでも配信される。** 守られているのは「画面」ではなく「データ」で、データ側は Supabase の RLS（マイグレーション021・023の `profiles.role = 'admin'` 判定）がサーバー側で効いている。

**結論：足すべきはパスワードではなくサーバーサイドのゲート。** 共有パスワード1本の追加には固有の弱さがある。
1. 誰が操作したか記録できない（4人＋CEOで共有するため）
2. 漏れたら全員分を替える必要がある。4人で共有すればSlack/LINEに平文で流れる
3. すでに Supabase Auth で個人ごとのアカウントがあるのに、それより弱い認証を上に重ねることになる

`/admin` にロードマップを置くこと自体は筋が悪くない。ただし正しい打ち手は **①新規テーブルにRLSを張る ②`middleware.ts` かServer Componentでサーバー側判定を入れる**。
※ これは既存 `/admin` 全体の弱点でもあり、**このロードマップツールとは独立した改善課題として起票する価値がある**。

### 2.2 `/clubtasks` が既に存在する

`app/(club)/clubtasks`（`@hello-pangea/dnd` によるD&D付き）で学生団体向けタスク管理が実装済み。
⇒ 自社運用ツールを `/admin` に別途作ると**機能が二重になる**。逆に、自社で使い倒して `/clubtasks` に還元する「ドッグフーディング」として設計するなら内製に強い理由が立つ（※今回は不採用。将来の選択肢として残す）。

### 2.3 `ibeck2/proofloop` は Public リポジトリ

GitHub Projects / Issues を使う案では致命的。**企業ロングリストや学生団体への個別アプローチ状況を書いた瞬間に営業情報が全世界に公開される。** 採用する場合は Private な別リポジトリ（例：`ibeck2/proofloop-ops`）が必須。

## 3. 混ぜてはいけない3つの層（設計の前提・合意済み）

| 層 | 中身 | 適した道具 |
| --- | --- | --- |
| **ロードマップ層** | 月次アウトプット・担当・依存・完了チェック | ガント／タイムライン |
| **実行層** | 企業ロングリスト200件、学生団体リスト、送信済み・返信あり | **テーブル（軽量CRM）** |
| **開発層** | 財務DX改良、AI記事のPR | GitHub |

**企業100社へのメールは「1タスク」ではなく「100レコード」。** これをガントに載せると即座に破綻する。ガントに載るのは「企業ロングリスト作成」「第1バッチ送信」というマイルストーンだけで、中身はテーブルで持つ。**この分離が設計の肝。**

## 4. 検討した3案と決定

### 案A：Notion（ロードマップ＋CRM）＋ GitHub（コード）
- ✅ Timelineビューでガント、依存関係プロパティ標準。企業リスト・団体リストを同一ワークスペースに持てる
- ✅ 非エンジニア作業に強い。CEOへの可視化がそのまま使える
- ⚠️ 開発タスクはGitHubに残り2箇所になる／無料プランのチーム制限は**未確認**

### 案B：GitHub Projects（Roadmapビュー）に一本化
- ✅ 無料。コードと同じ場所。AI記事パイプラインの「出力はPR」と噛み合う
- 🔴 **Public リポジトリ問題（2.3）。Private な ops リポジトリが必須**
- ⚠️ 200件のリスト管理をIssueでやるのは重く、実行層は結局スプレッドシートに逃げる

### 案C：Google スプレッドシート ＋ GitHub Issues（最小構成）← **✅ 採用**
- ✅ `contact@proofloop.jp` がGoogleアカウントのため追加契約ゼロ
- ✅ 学習コストが実質ゼロ＝**更新され続ける確率が一番高い**（兼業チームではこれが他の全部に勝つ、というのが採用理由）
- ✅ リスト管理はスプレッドシートが本来の土俵
- ⚠️ 依存関係の可視化は手作業。「終わったら自動で次の担当に回る」は作り込めない

### 内製（`/admin`）を採用しなかった理由
- 実装40〜80時間＝**月次capacityの1/3**。1月末ゴールが協賛案件である以上、その時間はアウトリーチに使うべき
- 2.1 のとおり `/admin` はサーバーサイドのゲートが無く、先に middleware と RLS の整備が要る。抱き合わせると重くなる
- **将来は筋が良い**：`/clubtasks` にガント・依存を足す機能として、自社の運用知見ごと製品に還元する道は案Cで運用しても後から取れる

## 5. セクション1：月次アウトプット・ツリー — 🚧 **承認待ち（ここで中断）**

### 逆算の起点：鶏と卵をどう破るか

> 企業に「学生団体に助成金を」と打診するには、**どの団体に何ができるか**が言えないといけない。
> 団体に「協賛が取れます」と言うには、**企業の見込み**がないといけない。

**破り方：団体側を先に薄く作る。** 理由3つ。
1. 団体リストは既に手元にある（掲載2,421団体）うえ、**東大・京大・早慶の人脈で直接アプローチできる**
2. 企業は実績ゼロだと門前払い。「東大のコンサル系団体N件が使っています」と言えて初めて土俵に乗る
3. 団体アウトリーチは8月から即着手できる（企業リスト作成は調査に時間がかかる）

### 月次ツリー（案・未承認）

**SEO・AI記事は全月を通した「下支え」レーン**として細く並走（月1〜2本）。1月末ゴールが協賛案件である以上、記事は主軸にしない。ただしドメイン価値は複利で効くので止めない。次回SEO PDCA（≈2026-08-22）の結果を見て投下量を調整する。

### 依存関係（ガントで矢印になる部分）

```
Resend認証 ──→ 団体メール送信 ──→ 返信・オンボーディング ──→ 実利用団体
                                                              ↓
                                            企業ロングリスト ──→ 企業打診 ──→ マッチング ──→ 案件
```

**Resend認証が全ての起点。** ここが詰まると8月が丸ごと死ぬ。最優先ブロッカーとして扱う（`docs/owner-todo.md` に未完項目として存在）。

### 先に潰すべきリスク3点（提示済み・回答待ち）

1. **特定電子メール法の確認が要る（8月着手前）。** 学生団体・企業への営業メールは同法の対象。原則オプトインだが、**団体がウェブで公表しているアドレス**への送信は例外規定に当たる可能性が高い、というのが現時点の理解。ただし**送信者の氏名・住所・受信拒否の通知先の表示は必須**。**法務判断のためオーナー確認事項**として起票する。上記の理解が正しいかも含めて要確認。
2. **「かなりある」を数値にしないとガントが引けない。** 利用団体10なのか50なのかで、8月のリスト件数もメール本数も変わる。1月末の目標値の確定が必要。
3. **総capacity 720〜1,440時間に開発が含まれる。** 財務DX改良・記事・`/companysearch` 改修を全部やるとアウトリーチが痩せる。**「開発は詰まった箇所だけ直す」**という原則を明示的に置くべき、というのが提案。
