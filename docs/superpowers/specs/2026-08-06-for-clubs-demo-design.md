## 1. 背景 — なぜ「手触りがない」のか

`/for-clubs` は既に機能紹介のZレイアウトとモック画面を持っている。にもかかわらず手触りが無い。コードを読んで原因が3つ特定できた。

1. **モックが灰色の箱。** `MockInboxKanban` などの中身は `bg-rule` の長方形が並んでいるだけで、実データも実UIもない。何の画面かが伝わらない。
2. **「（イメージ）」と明記している。** 読み手には「まだ無いものの絵」に見える。
3. **財務DXが載っていない。** 機能紹介は応募管理・タイムライン・イベント・タスク/メンバーの4本で、2026-07-26に本番稼働した会計・財務への言及が**ゼロ**。最も差別化される機能が訴求から抜けている。

副次的に、`MockChrome` のURLバーが `proofloop.app` と誤っている（正しくは `proofloop.jp`）。信頼性を訴求する面で自社ドメインを間違えている。

## 2. 確定した判断

| # | 論点 | 決定 |
| --- | --- | --- |
| 1 | デモの形 | **実データ入りの再現画面 ＋ 実際に触れるデモを1つ** |
| 2 | 触れるデモにする機能 | **会計・財務** |
| 3 | ページ構成 | `/for-clubs` ＝訴求／`/manual` ＝手順書／学生向けは `/guide` ハブ。**`/for-students` は作らない** |

### 判断2の理由

会計は「入力すると残高・費目別集計・予算対比が即座に動く」ため、触って価値が分かる。大学への収支報告という明確な痛みに直結し、他社の汎用ツールに無い差別化要素でもある。カンバンやD&Dは Notion / Trello で見慣れており、「ProofLoop ならでは」の訴求になりにくい。

### 実現可能性の検討（記録）

当初は Playwright で本番画面のスクリーンショットを撮る案を検討したが、**却下した**。団体画面はログインが必要で Claude はパスワードを扱えず、撮影に足るデータが本番DBに無い（タスク0件・イベント1件・会計3件）ためデモ団体を本番に作り込む必要が生じる。オーナー同席と本番データ汚染の両方が発生し、割に合わない。

代わりに「**画面は再現、計算は本物**」という構成を採る。`lib/finance/` の関数は純粋関数として切り出されており Supabase にも認証にも依存しないため、LPから直接呼べる。

## 3. 触れる会計デモ

### 3.1 構成

`components/for-clubs/FinanceDemo.tsx`（Client Component）。

架空の団体「**桜丘大学 ダンスサークル**」の会計期間が最初から入っている状態で表示する。大学名も架空にし、実在の大学・団体を想起させない。期首残高、既存の取引が数件、費目別の予算が設定済み。訪問者は日付・収支区分・費目・金額・摘要を入力して「記録する」を押すと、**残高・収支サマリ・費目別の予算対比バーがその場で更新される**。リセットも可能。

### 3.2 製品と同じコードを使う

計算には以下をそのまま呼ぶ。いずれも既存の純粋関数で、テスト済み。

| 関数 | ファイル | 用途 |
| --- | --- | --- |
| `currentBalance(openingBalance, txns)` | `lib/finance/balance.ts` | 残高 |
| `sumByKind(txns, kind)` | `lib/finance/balance.ts` | 収入・支出の合計 |
| `aggregateByCategory(...)` | `lib/finance/aggregate.ts` | 費目別集計と予算対比 |
| `summarize(...)` | `lib/finance/aggregate.ts` | 収支サマリ |

デモ用のデータは `lib/finance/types.ts` の `FinanceTransaction` / `FinanceCategory` / `FinanceBudget` の型をそのまま満たす。**型が合わなくなったらビルドが落ちる**ため、製品側の型変更にデモが自動的に追随を強制される。

### 3.3 表示する一文

デモの下に「**この計算は製品と同じコードが動いています**」と置く。誇張ではなく事実であり、再現画面との差を明示する信号になる。

### 3.4 置き場所

**ヒーローの直下。** スクロールせずに触れることを優先する。LPのセオリーでは課題提起の後だが、課題提起はヒーローのコピー自体（「LINEのDM管理、もう限界じゃないですか。」）が担っており、重ねる必要が薄い。

## 5. 再現画面の差し替えと表記

### 5.1 灰色の箱をやめる

現行 `Mock*` の中身を、実際の団体名・人名・日付・金額・ステータスが入った具体的な再現に差し替える。

**架空の団体名・人名を使う。** 実在する掲載団体の名前をLPの宣伝素材に流用するのは、`/listing-policy` で定めた「公表されている事実情報を掲載する」という趣旨と衝突する。

`MockChrome` のURLバーを `proofloop.app` → `proofloop.jp` に修正する。

### 5.2 表記を分ける（信頼性ファースト）

- **再現画面** … 「画面イメージ」表記を**残す**。再現である以上、本物と偽らない
- **会計デモ** … 表記を付けない。代わりに §3.3 の一文を置く

この差自体が「デモは本物だ」という信号になる。

### 5.3 色の制約

深紅（seal）は既にCTAボタンで2箇所使っており**上限に達している**（CLAUDE.md §3：静止状態で1画面2箇所まで）。**デモには深紅を使わない。** ink・mist・rule・graphite のみで組む。

## 7. テスト

デモは見せ物である以上、**数字が合っていないと逆効果**になる。純粋関数側は既にテスト済みなので、デモ固有の部分を担保する。

1. 初期データで「期首残高 ＋ 収入合計 − 支出合計 ＝ 表示残高」が一致する
2. 費目別集計の合計が収支サマリと一致する（取引の取りこぼしが無い）
3. 予算対比の対象費目が、費目マスタに実在する費目だけで構成されている

デモデータは `lib/for-clubs/financeDemoData.ts` に切り出し、UIコンポーネントから分離してテスト可能にする。
