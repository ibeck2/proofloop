# /clubtasks 大規模改修 設計

> 2026-08-17 ブレインストーミングで確定。次は `superpowers:writing-plans` で実装計画に落とす（フェーズごとに別々の計画・別々のPRに分ける）。

## 1. 背景・目的

`docs/superpowers/specs/2026-08-15-ceo-mtg-product-roadmap.md` の「タスク管理機能（修正）」で挙がっていた4要素のうち、レビュー移行・担当者アサイン通知は `2026-08-17-task-notifications-design.md` で実装済み。残る3案（表型＋カレンダー表示／カンバンのグルーピング／年度区切り）を起点に、Trello・Asana・ClickUp・Notion・Linear・monday.com・Basecamp等のTeam向けタスク管理SaaSを横断調査し、幅出しした改善案をまとめて実装する。

当初は「実装コストの低い順」で優先度をつける方針だったが、ブレスト中にオーナーから**方針転換**：コストの高低ではなく、機能として必要かどうかで判断する。結果、当初の3案に加えて次の4つを追加スコープとした。

- **成果物・アウトプットの添付**：ユーザーからの直接の指摘。競合はどこも標準搭載だがProofLoopには無かった
- **コメント・活動ログ**：CLAUDE.md §2「資産継承」「流動を蓄積に」という理念に直結する。単なる競合追随ではなく、代替わり後に判断根拠が参照できる状態を作る
- **チェックリスト**：1タスクを手順に分解する定番機能
- **定期タスク（繰り返し）**：週次・月次の反復業務が多い学生団体運営との相性

## 2. スコープと全体構成（3フェーズ）

| Phase | 内容 | スキーマ変更 | 理由 |
|---|---|---|---|
| **Phase 1** | 表型ビュー／カレンダービュー／カンバンのスイムレーン化（種別・担当者で行分割） | なし | 既存`tasks`テーブルのままUIだけ拡張できる。先に画面の骨格を固めておくと、Phase 2で増えるデータ（コメント数・添付数など）を各ビューにどう出すかの前提が定まる |
| **Phase 2** | 成果物添付／コメント・活動ログ／チェックリスト／定期タスク | あり（新規テーブル3＋列追加） | Phase 1のUI骨格の上に機能を乗せる |
| **Phase 3** | 年度アーカイブ | あり（列追加） | Phase 1・2で「タスクに何が紐づくか」が出揃ってから、「アーカイブ時に何を残すか」を決める方が手戻りがない |

各フェーズは別々の実装計画・別々のPRに分ける（CLAUDE.mdの「重要な変更は都度計画提示→承認」に沿う）。

### 今回スコープ外（将来検討）
- monday.com型の「任意列で動的グルーピング」（今回はカテゴリ／担当者の2軸固定のスイムレーンに留める）
- 本格的なサブタスク（担当者・期限を持つ子タスク）。今回はテキスト＋完了フラグのみのシンプルなチェックリスト
- 定期タスクの「ルールに従い先々の分を一括生成」方式（今回は完了時に次回分を1件だけ自動生成する方式を採用）
- コメントへの@メンション、リアクション等の付加機能

## 3. Phase 1 詳細

### 3.1 表型ビュー
列＝タイトル・ステータス・優先度・担当者・種別・期限。列ヘッダクリックでソート。行クリックで既存の編集モーダルを開く（新規モーダルは作らない）。

### 3.2 カレンダービュー
月表示。`due_date`があるタスクをその日のマスに表示し、クリックで既存の編集モーダルを開く。期限未設定タスクは対象外とし、既存のガントチャートと同様に「対象外件数のみ案内」する。

### 3.3 カンバンのスイムレーン化
カンバン上部に「フラット／種別ごと／担当者ごと」の切替を追加する。選択すると**列＝既存5ステータス固定、行＝選んだ軸**のグリッド表示になる（Jira・Azure DevOps・monday.com等で標準的な「スイムレーン」パターン）。

- 同じ行内で列をまたぐドラッグ：従来通りステータス変更のみ
- **行をまたぐドラッグ：ステータスに加えて、その行の軸（`category`または`assignee_id`）の値も変更する**（monday.com方式）。実装後に必ず実機で操作感を確認し、混乱するようであれば「行またぎドラッグ自体を禁止し、値の変更は編集モーダル経由に限定する」設計へ後退できるようにしておく

### 3.4 状態管理の変更
既存の`view`ステート（`"kanban" | "gantt"`）を`"kanban" | "gantt" | "table" | "calendar"`に拡張する。スイムレーンの軸（`"flat" | "category" | "assignee"`）はkanbanビュー内の別ステートとして持つ。

## 4. Phase 2 詳細

新規マイグレーションは`048`以降を使う（現状最新は`047_notification_preferences_anon_lockdown.sql`）。新規テーブルはすべて既存`tasks`のRLSパターン（`get_user_organization_ids`経由の組織スコープ）を踏襲する。

### 4.1 成果物・アウトプット添付

**データモデル**：新規テーブル`task_attachments`

| 列 | 型 | 内容 |
|---|---|---|
| `id` | uuid PK | |
| `task_id` | uuid FK→tasks | |
| `organization_id` | uuid FK→organizations | RLS判定用に非正規化で持つ（既存`tasks`と同じ設計思想） |
| `uploaded_by` | uuid FK→profiles | |
| `file_path` | text | Storageバケット内のパス |
| `file_name` | text | 元のファイル名 |
| `file_size` | bigint | |
| `mime_type` | text | |
| `created_at` | timestamptz | |

- Supabase Storageバケット`task-attachments`（非公開）を新設。パス規則：`{organization_id}/{task_id}/{uuid}_{filename}`（`clubfinance`の領収書写真と同じ発想）
- 読み出しは署名付きURL（`clubfinance`/`clubphotos`と同じ既存パターンを流用）
- 添付できるのは組織メンバー全員（担当者・作成者に限定しない）
- タスク削除時は`ON DELETE CASCADE`でメタデータ行も削除。Storage側のファイル実体の削除はPhase 2実装時にトリガーかクライアント側処理かを決める（既存の`clubphotos`削除パターンを踏襲する想定）

### 4.2 コメント・活動ログ

**データモデル**：新規テーブル`task_comments`

| 列 | 型 | 内容 |
|---|---|---|
| `id` | uuid PK | |
| `task_id` | uuid FK→tasks | |
| `organization_id` | uuid FK→organizations | |
| `author_id` | uuid FK→profiles | |
| `body` | text | |
| `created_at` | timestamptz | |

- タスク編集モーダル内にコメント欄を追加。時系列表示（新しい順）
- **新規コメント投稿時、タスク関係者（担当者・レビュー者・作成者。投稿者自身を除く）へメール通知**。既存の`notification_preferences`基盤にそのまま乗せる
  - `lib/types/notificationPreference.ts`の`NotificationType`に`"task_comment_added"`を追加
  - `lib/notifications/registry.ts`の`NOTIFICATION_REGISTRY`に`{ id: "task_comment_added", isOptional: true, isOrgScoped: true, ... }`を追加
  - 発火判定は`lib/tasks/taskNotificationTriggers.ts`と同じ流儀で純粋関数化してテスト（「コメント投稿者と通知先が別人」の条件のみ。ステータス条件は無し）
  - 送信APIは既存`/api/emails/task-notification/route.ts`に`type: "comment"`を追加する形で統合する（新規ルートは作らない。文面骨格が既存2種と同じため）
  - `is_notification_enabled`（SECURITY DEFINER）経由でオプトアウト確認してから送信。行が無い、または`enabled=true`なら送信

### 4.3 チェックリスト

**データモデル**：新規テーブル`task_checklist_items`

| 列 | 型 | 内容 |
|---|---|---|
| `id` | uuid PK | |
| `task_id` | uuid FK→tasks | |
| `text` | text | |
| `is_done` | boolean NOT NULL DEFAULT false | |
| `position` | integer | 表示順 |
| `created_at` | timestamptz | |

- 担当者・期限は持たない、テキスト＋完了フラグのみのシンプルな仕様
- カンバンカード上に「2/5」のような進捗バッジを表示する

### 4.4 定期タスク（繰り返し）

新規テーブルは作らず、`tasks`に列を追加する：`recurrence_rule text`（`'weekly' | 'biweekly' | 'monthly' | null`）。

**挙動**：タスクを「完了」に移行した時点で`recurrence_rule`が設定されていれば、以下を1件自動生成する（Todoist方式）。

- 引き継ぐもの：タイトル・種別（`category`）・優先度・担当者・レビュー者・`recurrence_rule`自体・チェックリスト項目（すべて未完了状態でコピー）
- 引き継がないもの：コメント・添付（毎回新しい記録として始まる）
- `due_date`：元の期限＋ルール分の間隔（元の期限が未設定なら今日＋間隔）
- 生成後のステータスは`todo`

生成ロジックは`lib/tasks/taskRecurrence.ts`に純粋関数（次回タスクのペイロードを計算する関数）として切り出し、TDDでカバーする。発火箇所は`handleSave`・`handleDragEnd`のステータス→`done`遷移箇所（既存の通知発火と同じ箇所）。

## 5. Phase 3 詳細（年度アーカイブ）

`tasks`に列を追加：`archived_at timestamptz`（null許容）、`archive_label text`（null許容。例：「2026年度」）。

- 代表者（`role IN ('owner','admin')`相当）が「年度アーカイブ」ボタンを押し、`archive_label`を入力すると、**その時点で未アーカイブの全タスクに`archived_at`（現在時刻）と入力した`archive_label`を一括で書き込む**
- **自動判定・日付ロジックは持たない**。団体ごとに年度の定義（4月始まり／代替わり時期）が揺れるため、CLAUDE.mdの既知の落とし穴（member_countのtext型扱い等、決め打ちで事故った例）を踏まえ、手動トリガーに統一する
- アーカイブ済みタスクは既存4ビュー（カンバン・ガント・表・カレンダー）から**デフォルトで除外**する
- 「アーカイブ履歴」フィルタまたは別画面から、`archive_label`ごとに参照専用で閲覧できる
- コメント・添付・チェックリストは`task_id`にぶら下がっているため、アーカイブ後もそのまま参照できる（削除しない）。**代替わり後も過去の判断根拠・成果物を追える**という、CLAUDE.md §2「資産継承」に直結する部分

## 6. 横断的な注意点

### 6.1 通知の露出増についての既知リスク
`4.2`のコメント通知は、既存の`/api/emails/task-notification`と同じ設計（APIルート側でDBの再確認をしない。フロントの判定を信頼する）を踏襲する。既存4ルート（承認・招待・応募・タスク通知）について`docs/task-board.md`に「ログイン済みの任意ユーザーがブランド悪用目的で任意宛先に送信できる」という既知リスクが記録済みで、オーナー確認の上で対処を見送っている（2026-08-17時点）。今回コメント通知を追加すると同じ設計の露出がもう1系統増えるため、**このリスクを本設計に明記するのみで、今回のフェーズでは対処しない**。対処する場合は別イシューとして扱う。

### 6.2 スイムレーンの行またぎドラッグ
3.3で触れた通り、行をまたぐドラッグでグルーピング軸の値まで変更する挙動は実装後に実機確認が必須。混乱するようであればモーダル経由の変更に後退させる。

## 7. テスト方針

- `lib/tasks/taskRecurrence.ts`（次回生成ロジック）を純粋関数化しTDDでカバー（期限あり／なし、各`recurrence_rule`の間隔計算、チェックリストのコピー）
- `lib/tasks/taskNotificationTriggers.ts`にコメント通知の発火判定を追加し、既存と同じ形式でテスト
- スイムレーンのグルーピング関数（タスク配列→行×列のグリッド構造への変換）を純粋関数化してテスト
- アーカイブ対象フィルタ関数（`archived_at`の有無での絞り込み）を純粋関数化してテスト
- UIコンポーネントに計算・判定ロジックを埋め込まない（CLAUDE.md §5の既存方針）

## 8. 実装順序（推奨）

1. Phase 1（表・カレンダー・スイムレーン）
2. Phase 2（優先順は実装計画作成時に決める。着手しやすさで言えばチェックリスト→添付→コメント→定期タスクの順が自然）
3. Phase 3（年度アーカイブ）

各フェーズごとに`superpowers:writing-plans`で実装計画を作成し、レビューを経てから着手する。
