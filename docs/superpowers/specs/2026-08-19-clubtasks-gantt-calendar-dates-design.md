# /clubtasks ガント・カレンダーの期間ドラッグ編集 設計

> 2026-08-19 ブレインストーミングで確定。次は `superpowers:writing-plans` で実装計画に落とす。
>
> オーナーからのフィードバック5点（①ガントの直感的な期限変更、②カレンダーでのドラッグ延長、
> ③タスク詳細の右サイドパネル化、④ガントの色を種別色に、⑤カンバンD&Dの重さ改善）のうち、
> このドキュメントは**①②④**（データモデルを共有するため一体で設計）を扱う。③は独立したUI改修、
> ⑤は新機能ではなく性能調査（`systematic-debugging`スキル向き）のため、別途それぞれ扱う。

## 1. 背景・目的

現状、タスクは`due_date`（期限）しか持たず、ガントチャートは表示のためだけに`created_at`（作成日時）を仮の開始日として使っている。これは編集不可能な代用値であり、「タスクの期間を直感的にドラッグで変更する」というオーナーの要望には応えられない。

ガント・カレンダー双方で「バーの両端をドラッグして開始日・期限を変更できる」体験を実現するには、**ユーザーが編集できる正式な開始日をタスクに持たせる**ことが前提になる。あわせて、ガントのバー色を現在のステータス色から、`/clubtasks`の他ビューと揃った種別色に変更する。

## 2. スコープ

### Phase 1（先に実装）
- `tasks`テーブルに`start_date`列を追加（DBスキーマ変更）
- ガントチャート：バー左端ドラッグで開始日、右端ドラッグで期限を変更
- ガントチャートのバー色を、ステータス色（`laneTintById`）から種別色（`categoryColor()`）に変更。「完了」タスクはバーにチェックマークアイコンを重ねて表示
- ドラッグの共通ロジック（純粋関数）を`lib/tasks/dateRangeDrag.ts`に新設

### Phase 2（Phase 1の基盤の上に実装）
- カレンダービューで、`start_date`〜`due_date`にまたがるタスクを複数日の横棒として描画（週をまたぐ場合はセグメントに分割）
- カレンダーのバー両端ドラッグで開始日・期限を変更（Phase 1と同じ`dateRangeDrag.ts`を再利用）

各フェーズは別々の実装計画・別々のPRに分ける（CLAUDE.mdの「重要な変更は都度計画提示→承認」に沿う）。

### 今回のスコープ外（将来検討）
- バー本体をドラッグしての平行移動（期間の長さを保ったまま日付をシフト）。今回は両端ドラッグ（伸縮）のみ
- 繰り返しタスク生成時の`start_date`引き継ぎ（後述4.4で「引き継がない」と決定）
- カンバンカード・表ビューへの開始日列の追加（今回はガント・カレンダーのみ）

## 3. データモデル変更

### 3.1 `start_date`列の追加
`tasks`に`start_date date null`を追加する。`due_date`と同じ「日付のみ・タイムゾーン非依存」の扱い。

### 3.2 ⚠️ 権限GRANTの対応が必須（実装時の最重要注意点）
本番の`tasks`テーブルを実測した結果、`authenticated`ロールへのINSERT/UPDATE権限は**テーブル単位ではなく列単位のGRANT**になっている（年度アーカイブ機能実装時に「テーブル単位REVOKE→許可列だけGRANT」パターンが適用された結果。`archived_at`/`archive_label`をRPC経由でしか書けなくする設計の副産物として、他の全列も明示的な列GRANTに変わっている）。

**`start_date`列を追加しても、この列GRANTリストに`start_date`を明示的に加えない限り、`authenticated`はこの列に一切書き込めない**（`profiles.role`の030・`clubtasks`アーカイブの057〜059と同型の罠）。マイグレーションは列追加と同じトランザクション内で以下を行う：

```sql
ALTER TABLE public.tasks ADD COLUMN start_date date;

GRANT INSERT (start_date) ON public.tasks TO authenticated;
GRANT UPDATE (start_date) ON public.tasks TO authenticated;
```

実装計画では、この変更を`migration-safety`スキルのチェックリストに従って書き、`rls-migration-reviewer`サブエージェントでレビューし、本番適用前に`BEGIN; ... ROLLBACK;`で列への書き込みが実際に通ることを検証する。

### 3.3 `start_date`が未設定のタスクの扱い
既存タスクは全て`start_date IS NULL`から始まる。ガント・カレンダーの表示では、`start_date`が無ければ従来通り`created_at`を仮の開始日として使う（表示のみ・編集不可）。**ユーザーが左端をドラッグして開始日を変更した時点で、その値が`start_date`として確定・保存される。**

## 4. ドラッグの実装方式

### 4.1 方式：カスタムポインタードラッグ（新規ライブラリ追加なし）
ガント・カレンダーとも、バーの両端に小さな「つまみ」要素を置き、`pointerdown`→`pointermove`→`pointerup`で独自にドラッグを実装する。既存のカンバンで使っている`@hello-pangea/dnd`はリスト内の並べ替え・移動を想定したライブラリで、「連続値（日付）をドラッグで変える」用途には向かないため、この部分だけ切り離して自前実装する。

- ドラッグ中はコンポーネントのローカルstateで見た目だけプレビューし、DBへは書き込まない
- 指を離した（`pointerup`）時点で1回だけ、変更後の日付を親（`page.tsx`）経由でSupabaseに書き込む（カンバンの`handleDragEnd`と同じ「ドラッグ中はローカル、確定時に1回書き込み」パターン）

### 4.2 ピクセル⇄日付の変換（純粋関数）
新規`lib/tasks/dateRangeDrag.ts`に、UIから独立した計算ロジックを切り出す：

- `pixelDeltaToDayDelta(deltaPx: number, dayWidthPx: number): number` — ドラッグ量（px）を日数に変換（四捨五入）
- `applyDragToRange(current: { startDate: string; dueDate: string }, edge: "start" | "due", dayDelta: number): { startDate: string; dueDate: string }` — 日数分だけ該当する端をずらし、**開始日が期限を超えないようクランプする**（左端が右端を追い越したら同じ日に揃える。右端も同様）

ガントは元々`DAY_WIDTH`（28px）固定なので4.2をそのまま使える。カレンダーは週7列のグリッドなので、ドラッグ中のポインター位置を「グリッド全体の横幅 ÷ 7」で日カラムに変換してから同じ関数に渡す（変換部分はビュー固有・日数への変換以降は共通）。

### 4.3 開始日が期限を超える／同じ日になるケース
1日単位の粒度なので、開始日＝期限（1日だけのタスク）は許可する。それより先に交差しようとした場合は、ドラッグ中のプレビュー・確定後の保存とも「反対側の端と同じ日」にクランプする（4.2の`applyDragToRange`が担保）。

### 4.4 繰り返しタスク生成時の`start_date`
`buildRecurringTask`（`lib/tasks/taskRecurrence.ts`）が生成する次回タスクには、**`start_date`を引き継がない**（`null`のまま）。理由：現状`due_date`だけをルールに従ってずらす設計で、期間の長さを保ったまま`start_date`も computed するのはこの機能追加のスコープを超える（YAGNI）。次回タスクは生成時点で`start_date IS NULL`になり、表示は3.3の`created_at`代用に従う。

## 5. ガントチャートの詳細（Phase 1）

### 5.1 バー色
`GanttView.tsx`の`tint = laneTintById[status] ?? "#002B5C"`を`categoryColor(task.category)?.hex ?? "#9AA5B1"`（種別未設定はrule寄りの中間グレー）に置き換える。行ラベル横に既にある種別ドット（前回実装）と、バー本体の色が一致するようになる。

### 5.2 完了マーク
`status === "done"`のバーには、`CheckCircle2`アイコン（他ビューと同じ意匠）をバー内に小さく重ねて表示する。バーの色自体はステータスに関わらず種別色のまま。

### 5.3 ドラッグ操作
バーの左端・右端それぞれに幅数pxの透明な「つまみ」領域を置き、`pointerdown`で開始。`pointermove`でプレビュー（バーのleft/widthを直接更新）、`pointerup`で`onDateRangeChange(taskId, { start_date? , due_date? })`を親に通知し、`page.tsx`側で1回のSupabase `update`を発行する。

## 6. カレンダービューの詳細（Phase 2）

### 6.1 複数日バーの描画
現状`CalendarView.tsx`は日付セル内にその日が期限のタスクを1行ずつ表示するだけで、複数日にまたがる概念を持たない。Googleカレンダーの終日イベントと同じ考え方で、週（7列グリッドの1行）ごとに、その週と交差するタスクの区間をバーのセグメントとして描画する：

- タスクの`start_date`（無ければ`created_at`）〜`due_date`の区間と、その週の7日間との交差区間を計算
- 交差区間の開始が週の初日より前から続いている場合は、バーの左端を丸めない（前の週から続いている見た目）。終了が週の最終日より後に続く場合も同様に右端を丸めない
- 同じタスクが複数週にまたがる場合、週ごとに別のセグメント（DOM要素）として描画される（これが標準的なカレンダーUIの実装パターン）

### 6.2 ドラッグ操作
週グリッドの横幅を7等分した1日ぶんの幅を基準に、ポインターのX座標から日カラムを算出し、5.3と同じ「つまみ→pointermove→pointerup」の流れで`start_date`/`due_date`を更新する。週をまたぐドラッグ（例：先週の月曜から今週の水曜まで伸ばす）にも対応する。

## 7. テスト方針
- `lib/tasks/dateRangeDrag.ts`を純粋関数化し、TDDでカバーする：
  - `pixelDeltaToDayDelta`：正負のpx量・端数の丸め
  - `applyDragToRange`：左端ドラッグ・右端ドラッグそれぞれの通常ケース、交差しようとした場合のクランプ
- カレンダーの「週との交差区間計算」ロジックも`lib/tasks/`の純粋関数として切り出し、テストする（週開始日・週終了日・タスクの区間を受け取り、その週内での描画開始日・終了日・左右を丸めるかどうかを返す）
- UIコンポーネント（`GanttView.tsx`・`CalendarView.tsx`）は表示とポインターイベントの配線のみを持ち、日付計算ロジックは持たない（CLAUDE.md §5の既存方針）
- マイグレーションは本番`BEGIN; ... ROLLBACK;`で、`start_date`列への書き込みが実際に通ることを検証してから適用する
