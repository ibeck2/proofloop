# SEO PDCA スキル 実装計画

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** GSC/GA4 を月次で解析し、ページ別スコアカード＋優先度付き改善提案を出す半自動 PDCA スキルと、その発火リマインダー（SessionStart フック）を用意する。

**Architecture:** link-freshness と同一構成（SessionStart フック `.mjs` ＋ スタンプファイル `YYYY-MM-DD` ＋ `SKILL.md`）。フックが28日経過を判定してリマインドし、ユーザーが `/seo-pdca` を実行。スキルは GSC(Ahrefs MCP)＋GA4(ブラウザ)を取得してレポートを `docs/seo/reports/` に出力。実装（Act）は承認制で対象外。

**Tech Stack:** Node ESM フック（依存なし・標準ライブラリのみ）、Markdown スキル、`.claude/settings.json` の hooks、Ahrefs MCP（`gsc-*`）、`claude-in-chrome`（GA4）。

## Global Constraints

- 設計仕様は `docs/superpowers/specs/2026-07-25-seo-pdca-design.md`。すべてのタスクはこれに従う。
- ペースは **28日**（月次）。link-freshness は30日だが本スキルは28日で揃える（4週）。
- フックは **何があってもセッション開始を妨げない**（読めない/壊れている場合は黙って終わる）。link-freshness フックと同じ堅牢性方針。
- スタンプファイルは `docs/seo/reports/.last-run`、`YYYY-MM-DD` 1行のみ受け付ける。
- 自動実行では **本番を一切触らない**（実装は承認制の別ステップ）。
- 広告リンク（バリューコマース `ck.jp.ap.valuecommerce.com/...`）は**叩かない**（計測が歪む）。分析で外部リンクを踏む必要は本スキルには無いが、原則として遵守。
- コミットメッセージ・スキル本文は日本語で可。

Create `.claude/hooks/seo-pdca-reminder.mjs`:

```javascript
// SEO PDCA 点検リマインダー（SessionStart フック）
//
// docs/seo/reports/.last-run に記録された前回実行日を読み、28日を過ぎていたら
// セッション開始時に一言だけ出す。GSC/GA4 の解析→改善提案は「忘れる」ことが
// 最大の失敗要因なので、思い出す仕掛けをここに置いている。
//
// 方針：何があってもセッション開始を妨げない。読めない・壊れている場合は黙って終わる。

import { readFileSync } from "node:fs";
import { dirname, join } from "node:path";
import { fileURLToPath } from "node:url";

const INTERVAL_DAYS = 28;

try {
  const here = dirname(fileURLToPath(import.meta.url)); // <root>/.claude/hooks
  const stampPath = join(here, "..", "..", "docs", "seo", "reports", ".last-run");

  let lastRun = null;
  try {
    const raw = readFileSync(stampPath, "utf8").trim();
    // YYYY-MM-DD のみ受け付ける。壊れた値で誤ったリマインドを出さないため。
    if (/^\d{4}-\d{2}-\d{2}$/.test(raw)) {
      const parsed = new Date(`${raw}T00:00:00Z`);
      if (!Number.isNaN(parsed.getTime())) lastRun = parsed;
    }
  } catch {
    // ファイルが無い＝一度も実行していない。下で「未実施」として扱う。
  }

  if (lastRun === null) {
    console.log(
      "【SEO PDCA点検】まだ一度も実行されていません。" +
        "GSC/GA4 で各ページの反応を解析し改善提案を出すには seo-pdca スキル（/seo-pdca）を使ってください。"
    );
  } else {
    const elapsedDays = Math.floor((Date.now() - lastRun.getTime()) / 86_400_000);
    if (elapsedDays >= INTERVAL_DAYS) {
      const ymd = lastRun.toISOString().slice(0, 10);
      console.log(
        `【SEO PDCA点検】前回の解析は ${ymd}（${elapsedDays}日前）です。` +
          "月1回（28日）を目安にしているため、seo-pdca スキル（/seo-pdca）で回してください。"
      );
    }
  }
} catch {
  // 想定外の失敗でセッション開始を止めない。
}
```

# SEO PDCA 点検

## なぜやるか

ProofLoop は「B2Cメディアで検索流入を貯め、B2B獲得につなげる」二層戦略（CLAUDE.md §2）。その入口である検索流入は、**計測して直し続けない限り伸びない**。この点検は、GSC（順位・CTR・表示）と GA4（回遊・成果）から各ページの反応を読み、次に直すべき場所を優先度つきで出すためのもの。

**このスキルは分析と提案までしか行わない。** 改稿や記事追加といった実装は、提案から選んで承認フロー（CLAUDE.md §0）で別途行う。自動実行で本番は触らない。

## 前提

- **GA4 はログイン済みブラウザが要る。** このスキルは同席実行が前提（リマインドを見て手動起動する半自動モデル）。ブラウザが繋がっていない場合は GSC 分析だけ先に行い、GA4 分は「未取得」として明記する。
- GSC は Ahrefs MCP の `gsc-*` ツールで取得する（Rank Tracker 登録は不要）。
- 広告リンク（バリューコマース）は**叩かない**。本スキルで外部リンクを踏む必要はない。

## 手順

### 1. 前回レポートを読み、モードを判定する

- `docs/seo/reports/` の最新レポートを読む（無ければ「初回」）。
- **データ成熟度モードを判定**：GSC の総クリック/インデックス数が僅少なら **初期モード**（インデックス健全性＋ベースライン計測中心）、流入が貯まっていれば **成熟モード**（改稿・押し上げ中心）。レポート冒頭に明記する。

### 2. GSC データを取得（Ahrefs MCP・自動）

`gsc-*` ツールで、直近28日 vs 前28日の比較を基本に取得：

- ページ別：クリック / 表示回数 / CTR / 平均掲載順位（`gsc-pages`, `gsc-pages-history`, `gsc-page-history`）
- 主要ページのクエリ（`gsc-keywords`, `gsc-keyword-history`）
- **「あと一歩」クエリ＝平均掲載順位 5〜20 位**（1ページ目に最短で届く勝ち筋。最優先の分析軸）
- インデックス健全性（登録ページ数の推移）

> 監視の主対象はコンテンツ面：`/gpa`・`/guide/*`・`/baito`・`/baito/simulator`・`/guide/study-abroad/recommend`。団体ページ（2,400+）は個別でなく**集計**（合計流入・インデックス率）で扱う。

### 3. GA4 データを取得（ブラウザ・同席）

`claude-in-chrome` で GA4（プロパティ ProofLoop / `G-6DW8LF5H7Q` / `contact@proofloop.jp`）を開き、前期比で取得：

- ページ別エンゲージメント（表示回数・エンゲージメント率・平均エンゲージメント時間）
- キーイベント／主要イベント：`gpa_calculate`・`simulator_complete`・`study_abroad_complete`・`affiliate_click`・`simulator_share`
- 流入元（オーガニック比率・参照元）

複数のChromeが接続されている場合は、GA4にログイン済みのものを選ぶ（AskUserQuestionで確認）。ブラウザが無ければこの節を「未取得」として飛ばす。

### 4. ページ別スコアカードにまとめ、4分類にフラグ

GSC（可視性）× GA4（回遊・成果）を突き合わせ、各ページを分類する：

| フラグ | 定義 | 次アクションの方向 |
| --- | --- | --- |
| 伸びてる | クリック or 順位が前期比で改善 | 伸ばす（内部リンク強化・関連KW拡張） |
| 落ちてる | クリック or 順位が前期比で悪化 | 直す（原因診断・改稿） |
| あと一歩 | 主要KWが5〜20位 | 押す（該当KW狙いのH2/FAQ追加） |
| 流入ゼロ | インデックス済みだが表示・流入が僅少 | 診断（インデックス/内容/内部リンク） |

### 5. 診断して、優先度付きの改善提案を出す

フラグ付きページごとに、**根拠つきの具体案**を出し、**インパクト × 手間**でランキングする。断定できないものは「要確認」に寄せる。例：

- 「`/guide/money` は『大学生 奨学金』で14位。該当KW狙いの H2 と FAQ を追加して1ページ目を狙う（インパクト大・手間中）」
- 「`/gpa` は表示回数に対し CTR が SERP 平均より低い → title/meta を改稿（インパクト中・手間小）」

### 6. 前回提案の結果を検証する（ループを閉じる）

前回レポートのランク付きアクションを1件ずつ照合する：

1. 実装されたか（git 履歴で該当コミット/PR を確認）
2. 実装したなら、対象ページの該当指標が動いたか（GSC/GA4 の前期比で検証）
3. 動かなかった提案は原因を考察し、取り下げ or 別アプローチへ差し替える

これをレポート冒頭の「前回の提案の結果」に書く。**初回はこの節を「初回のため対象なし」と明記する。**
