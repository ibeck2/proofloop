## 1. D9：応募（ATS・応募DM）をメンバー起点に移す

### 何が問題か

設計書 §2.1 は「`organizations.user_id` は権限判定に使われていない（実質的に死んだ列）」としていたが、
これは **`organizations` の UPDATE ポリシーに限った話**だった。

claim動線は乗っ取り対策として（正しく）`organizations.user_id` を書き換え不可にした。
そのため **claim経由のオーナーはこの列に載らない**。ところが応募まわりのRLSはこの列を見ている。

⇒ **`granted_level='full'` で承認しても `/clubats` の応募一覧と応募DMが常に0件になる。**

### 直す対象：`organizations.user_id` を参照している5本（本番実測 2026-08-12）

| テーブル | ポリシー | cmd | 現在の条件 |
| --- | --- | --- | --- |
| `applications` | `Club admins can view applications to their club` | SELECT | `organization_id IN (SELECT id FROM organizations WHERE user_id = auth.uid())` |
| `applications` | `Club admins can update applications to their club` | UPDATE | 同上（USING / WITH CHECK 両方） |
| `application_messages` | `Club admins can view messages for their club` | SELECT | `application_id IN (SELECT a.id FROM applications a JOIN organizations o ON a.organization_id=o.id WHERE o.user_id=auth.uid())` |
| `application_messages` | `Club admins can send messages` | INSERT | 上の条件 ＋ `auth.uid() = sender_id` |
| `application_messages` | `Club admins can update read_at` | UPDATE | 上の条件（USING / WITH CHECK 両方） |

**学生側のポリシー（`Students can ...` 4本）は触らない。** `user_id = auth.uid()` で正しく動いている。

### 🚨 この修正で最も踏みやすい罠

**「`can_manage_applications` を条件にする」を素直にやると、既存の自作団体オーナーが全員締め出される。**

- `organization_members.can_manage_applications` の既定値は **false**
- `app/(club)/clubdashboard/OrganizationProfileForm.tsx:483` は自作団体の owner 行を
  **権限フラグを一切指定せずに** INSERT している（`{organization_id, user_id, role:'owner'}` のみ）
- ⇒ 自作団体のオーナーは `role='owner'` だが `can_manage_applications=false`

これは **C1（限定承認がDBレベルで無効だった件）とまったく同じ形の罠**。
033 で `get_user_admin_organization_ids` に `can_manage_members` を要求する案を却下したのと同じ理由。

### 採るべき条件式

```
role IN ('owner','admin')  OR  can_manage_applications
```

これなら：

| 誰 | role | can_manage_applications | 応募が見えるか |
| --- | --- | --- | --- |
| 自作団体のオーナー | owner | false（既定） | ✅ 見える（roleで通る） |
| claim フル承認 | owner | true | ✅ 見える |
| **claim 限定承認** | **member** | **false** | ❌ **見えない（設計どおり）** |
| 招待された一般メンバー | admin（招待の既定） | true（招待の既定） | ✅ 見える |

設計 §3 の「限定権限は他人の個人情報に触れさせない」が、**DBレベルで**成立する。

### 実装の形

`can_manage_org_finance` と同じ形の SECURITY DEFINER 関数を1本作り、5本のポリシーから呼ぶ。

```sql
CREATE OR REPLACE FUNCTION public.can_view_org_applications(p_org uuid)
RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public AS $$
  SELECT EXISTS (
    SELECT 1 FROM public.organization_members m
    WHERE m.organization_id = p_org
      AND m.user_id = auth.uid()
      AND (m.role IN ('owner','admin') OR m.can_manage_applications)
  );
$$;
```

- **`auth.uid()` を関数内部で見る**こと。引数で受け取ると誰の権限でも問い合わせられる関数になる
- `REVOKE EXECUTE ... FROM anon` を明示する（`REVOKE ... FROM PUBLIC` は Supabase では効かない）
- マイグレーション番号は **035**

`application_messages` 側は `applications` を経由するので、
`application_id IN (SELECT a.id FROM applications a WHERE public.can_view_org_applications(a.organization_id))` の形になる。

### 移行リスク：実測でほぼゼロ（2026-08-12）

| 確認項目 | 実測 |
| --- | --- |
| `organizations.user_id` が入った団体 | **1件** |
| そのうちメンバー行が無い（＝移行で権限を失う）団体 | **0件** |
| `organization_members` の総行数 | 1件（owner・全フラグtrue） |
| `applications` の行数 | **0件** |
| `application_messages` の行数 | **0件** |

**応募データが1件も無いうちに直せる。** これがいま着手する最大の理由。

### 検証（本番書き込み禁止・`BEGIN; … ROLLBACK;` で行う）

`SET LOCAL ROLE authenticated` ＋ `request.jwt.claims` で `auth.uid()` を差し替え、
次の4者で見え方が期待どおりか確かめる：自作オーナー／フル承認claim／**限定承認claim（見えないこと）**／無関係の第三者。

### 完了条件

- 5本のポリシーが `organizations.user_id` を参照しなくなる
- 自作団体オーナーの既存アクセスが維持される
- 限定承認の claim オーナーが応募に到達**できない**ことを実測で確認
- 設計書 §10.5.3（いまは「別タスク」と書いてある）を「解決済み」に更新
- リスク台帳・タスクボード・タスクシート（D9）を更新

## 2. D10：`/organizations/[id]` に ISR を入れる

### 現状

`app/organizations/[id]/page.tsx` は Server Component。
React の `cache()` は使っているが、これは**1リクエスト内のメモ化**でしかない
（`generateMetadata` と本体で同じ問い合わせが2回走るのを防ぐためのもの）。
**リクエストをまたぐキャッシュは効いておらず、1アクセスごとに毎回DBに当たる。**

通知1,400件で流入が集中するのはまさにこの経路。

### ⚠️ 素直に `export const revalidate = 60` としてはいけない

`claim_status` は **`page.tsx` のサーバー側で取得**され（`ORG_COLUMNS` に含まれる・38行目）、
props で `OrganizationDetailClient` に渡っている（122行目）。
クライアント側は `claimStatus === "claimed"` のときだけ申告フォームを描画する（`OrganizationDetailClient.tsx:950`）。

⇒ ISR だけ入れると、**凍結した直後でも最大N秒は古い状態が表示される。**
凍結は「乗っ取りを見つけて緊急停止する」機能なので、ここが遅れるのは避けたい。

### 採るべき形：ISR ＋ オンデマンド再検証

1. `export const revalidate = 300`（5分程度）を入れる
2. **claim の状態が変わったときだけ、その団体のページを明示的に再検証する**
   - 変更が起きるのは `decide_claim` / `revoke_claim` / `submit_dispute` / `resolve_dispute` の4つ
   - いずれもクライアントから RPC を呼んでいるので、**成功後に `/api/revalidate` を叩く**
   - Route Handler で `revalidatePath('/organizations/[id]', 'page')` もしくは
     `revalidateTag(`org:${id}`)` を実行する
   - ⚠️ **このAPIは誰でも叩ける状態にしない。** 秘密トークンを要求するか、
     `is_system_admin()` 相当の確認を通す。無防備だと再検証を連打されてISRの意味が消える

これで「普段はキャッシュが効き、凍結・引き取りの瞬間だけ即座に反映される」。

### 併せて確認すること

- `ListingNotice` や `generateMetadata` がリクエスト固有の情報（cookie / headers）を使っていないか。
  使っていると Next.js が動的レンダリングに落として ISR が効かない
- `OrganizationDetailClient` がクライアント側で取得しているデータ（イベント・写真・口コミ）は
  ISR の対象外。ここは 034 の索引で軽くなっている
- **効果の実測を残す**こと。入れる前後で同一ページの応答時間を比較する

### 完了条件

- 同じ団体ページへの2回目以降のアクセスがDBに当たらないことを確認
- claim の状態変更後、**待たずに**表示が変わることを確認
- 再検証APIが無防備でないことを確認

## 4. 作業のときに必ず守ること

- **本番DBへの書き込みとスキーマ適用はオーナー承認が要る。** 検証は `BEGIN; … ROLLBACK;` で行う
- **ロジックは純粋関数に切り出してテストを書く**（CLAUDE.md §5）。UIに分岐を残さない
- 色は6色トークンのみ。`Button` の `secondary` は深紅なので副次ボタンに使わない（`outlineMuted`）
- `npm run dev` と `npm run build` を同時に走らせない
- **`REVOKE ... FROM PUBLIC` は Supabase では効かない。** `anon` へ明示的に `REVOKE` する
- 列レベル `GRANT` を絞るときは呼び出し側が `upsert` かを確認する（030 で新規登録が全滅した）
- **RLS を触る前に `pg_policies` を実測する。** フラグ列があっても、それを見ているポリシーが
  存在するとは限らない（C1・D9 とも、この思い込みが原因）
