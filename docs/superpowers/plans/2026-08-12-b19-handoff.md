## 2. 技術的な事実（本番実測・2026-08-12）

### 2.1 `revoke_claim` RPC 自体は既に存在する（033で実装済み）

`public.revoke_claim(p_claim_id uuid, p_reason text)` は本番に既にある。やっているのは：

1. 申請者本人の `organization_members` 行を削除
2. `decided_at` 以降に作られたメンバー行を削除（claimの権限で後から追加された分）
3. その団体の未受諾 `organization_invitations` を全削除
4. `organizations.claim_status` を `claimed` → `unclaimed` に戻す（`frozen` のときは触らない）
5. `organization_claims.status` を `revoked` に

**呼び出し元はアプリに1つも無い。** `resolve_dispute`（申立て対応のuphold分岐）が内部から呼んでいるだけで、
`/admin/claims` からの直接呼び出しは無い。

### 🚨 2.2 見つけた実装ギャップ：`revoke_claim` は掲載内容を巻き戻さない

`revoke_claim` の定義を読むと、**`organization_members` と `organization_invitations` の掃除しかしていない。**
`organizations` の掲載内容（`restore_organization_columns` の呼び出し）は一切無い。

一方、`resolve_dispute` のuphold分岐（`032_dispute_rate_limit.sql`）は、`revoke_claim` を呼んだ**あとで**
別途こうしている：

```
IF NOT d.froze_organization THEN
  -- pre_claim スナップショットを取得して restore_organization_columns で戻す
END IF;
```

つまり、**「掲載内容を戻す」ロジックは `resolve_dispute` 側にあり、`revoke_claim` 自体は持っていない。**

⇒ B19で `/admin/claims` に「発行の取消」ボタンを付けて `revoke_claim` を直接呼ぶだけだと、
**メンバー・招待は消えるが、乗っ取り犯が書き換えた掲載内容はそのまま公開され続ける。**
これが `docs/task-board.md` に「却下時の復元も同時に直す」と書かれていた懸念の実体
（文言は「却下時」だが、実際に危ないのは**revoke単独パスの復元漏れ**の方だった）。

対応方針の候補（ブレインストーミングで確定させる）：
- (a) `revoke_claim` 自体に `restore_organization_columns` 呼び出しを足す（`resolve_dispute` 側の重複コードは削る）
- (b) `/admin/claims` の「発行の取消」ボタンから、`revoke_claim` とは別に復元RPCも呼ぶ
- (a)の方が一貫性が高い（剥奪の経路が2つあっても復元ロジックは1箇所になる）が、
  `resolve_dispute` 側の「`froze_organization` なら既に巻き戻し済みなので二重に戻さない」
  という条件分岐と整合させる必要がある

### 2.3 `/admin/claims` は「承認待ち」しか一覧に出していない

`list_pending_claims()` RPCは `WHERE c.status = 'applied'` のみを返す。**承認済み（`approved`）の
claimは`/admin/claims`のどこにも一覧表示されていない。**

⇒ 「発行の取消」ボタンをどこに置くかが未解決。候補：
- 新しいRPC（例：`list_approved_claims()`）を作り、`/admin/claims` に「承認済み」セクションを追加
- 既存の一覧とは別に、団体名や申請者で検索する形にする
- どちらにせよ、承認済みclaimの一覧を返す経路が今は存在しない（新規に作る必要がある）

### 2.4 権限・RLSまわりで踏襲すべきパターン（このセッションで確立）

- 判定関数は `SECURITY DEFINER` ＋ `SET search_path = public` ＋ `auth.uid()` を**関数内部**で参照
- Supabaseでは `REVOKE ALL ... FROM PUBLIC` が効かない。`REVOKE EXECUTE ... FROM anon` を明示する
- `role IN ('owner','admin') OR フラグ` の形（フラグ単独だと既定値falseの既存オーナーを締め出す）
- RLSを触る前に必ず `pg_policies` を実測する（フラグ列があっても見ているポリシーが無いことがある）
- 本番検証は `BEGIN; … ROLLBACK;` で、複数の立場（自作オーナー・claimフル・claim限定・第三者）を
  同一トランザクション内で比較する

## 3. 進め方

1. `superpowers:brainstorming` から始める（CLAUDE.mdのPlan Mode要件）。まず2.2のギャップを
   どう塞ぐかの方針をユーザーと合意する。2.3の「一覧のどこに出すか」も合わせて決める
2. 設計→計画→実装は、このセッションで使った流れ（`writing-plans` →
   `subagent-driven-development`、Task 1つずつ「実装→タスクレビュー」、最後に全体レビュー）を踏襲してよい
3. RLS/RPCを変更する場合、必ず `BEGIN; … ROLLBACK;` で検証してから本番適用の承認を得る
4. 実装後、`docs/task-board.md`・タスクシート（`node docs/models/build-task-sheet.mjs
   "ProofLoop_タスクシート_2026-08-07.xlsx"` で再生成）・`.superpowers/sdd/progress.md` を更新する
5. デプロイが必要な変更が出たら、`git push origin main` の実行可否を確認してから push する
   （B18で「pushし忘れて本番が古いまま」という事故が起きたので、実装完了後は忘れずpushする）
