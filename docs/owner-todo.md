## ✅ 障害対応（2026-08-10 発生・同日復旧）

- [x] **Supabase プロジェクトが応答しない。ログイン・新規登録・DB参照がすべて不能**（完了 2026-08-10）
  - **原因は NANO インスタンスのディスクI/O枯渇だった。** ダッシュボードのメトリクスで
    **COMPUTE 100%・DISK IO 100%**（CPU 24%・MEMORY 55%）を実測。
    ディスク容量は `0.27 GB / 8 GB`・DBサイズ 16MB で、**容量不足ではなくI/O枠の枯渇**。
    NANO は I/O バジェットが小さく、使い切ると autovacuum すら起動できずDB全体が停止する。
  - **対応（Claude がブラウザ操作で実施）**：
    1. プロジェクトを再起動 → 認証エンドポイントが `522` → `521` → `400` と回復
    2. コンピュートを **NANO → MICRO** に変更（メモリ 0.5GB→1GB、共有CPU→2コア専有）。
       **時間単価は同額（$0.01344/hour）で月額 $9.68 → $9.68 の +$0.00。** Supabase の「Free Upgrade」枠
  - **結果**：認証 20秒タイムアウト → **34〜40ms**、REST → **76〜97ms**。`/login` も HTTP 200。
    データは無傷（団体 2,421件・ユーザー 3件）、033 の修正も維持されている。
  - ✅ **`/mypage` の保存も実地確認済み**（2026-08-10）。オーナーがログインして保存を実行し、
    `profiles` の該当行が `2026-08-10 04:01:45+00` に更新されたことをDBで確認。
    030 適用（08-08）以降、初めて成功した profiles への書き込み。**C3 はこれで完全に解消。**
  - ⚠️ **NANO には戻せない**（ダッシュボード上でロック表示）。問題ない。

## （参考・旧記載）デプロイ前に必須（2026-08-10 追加・対応済み）

- [x] **Vercel に `ADMIN_BASIC_USER` / `ADMIN_BASIC_PASSWORD` を設定する**
  - `/admin` 配下に HTTP Basic 認証を被せた（`middleware.ts`・リスク S1 への対処）。
  - ⚠️ **この2つを設定しないまま本番へ出すと、`/admin` 全体が 503 になり運営自身が入れません。**
    「未設定なら素通し」にしなかったのは意図的です。入れたつもりの防壁が黙って存在しない状態は、
    いちばん危ない失敗の仕方なので。
  - 設定場所：Vercel → プロジェクト → Settings → Environment Variables。
    **Production / Preview の両方**に入れてください（Preview を忘れるとプレビューURLで 503 になります）。
  - ⚠️ **`NEXT_PUBLIC_` を付けないこと。** 付けるとブラウザに配信されて意味が無くなります。
  - パスワードは推測されにくいものを。**これは共有パスワードなので「誰が操作したか」は残りません。**
    各ページの `profiles.role === 'admin'` 判定と RPC の `is_system_admin()` はそのまま残っており、
    Basic 認証はその外側に重ねた層です。
  - 📌 設定後の確認：`https://proofloop.jp/admin` を開いてブラウザの認証ダイアログが出れば成功。
  - 📌 副作用：Basic 認証のダイアログが出るため、**Claude のブラウザ自動操作から `/admin` を直接開けなくなります**。
    必要になったらオーナーが認証を通した状態のタブを使ってください。
